Helix

Institutional memory for clinical data mapping

Clinical trials · regulated life sciences

The context

Decision Intelligence Platform for Clinical Data — capturing, versioning and reusing mapping decisions across the ODM → SDTM → ADaM transformation pipeline.

The problem

Every clinical study re-derives the same data-mapping decisions from scratch. The reasoning lives in spreadsheets and in people's heads, it is lost when staff move on, and regulators still expect a defensible audit trail for every one of them.

What we built

  • CDISC ODM v1.3.2 ingestion with schema validation, then mapping decisions carried through review, comment and approval chains
  • Cross-study precedent reuse — semantic search over prior decisions, copied forward with lineage tracking and conflict resolution
  • AI-assisted mapping suggestions with confidence scoring, plus nine anomaly detectors for cross-study inconsistency
  • Executable SAS, R and Python code generated straight from approved decisions
  • Virtual trial simulation: a 17-tool agent runs synthetic cohorts visit by visit, with synthetic control arms and ML enrollment forecasting
  • Regulatory output — eCTD Module 5 packages, Define-XML 2.1, ClinicalTrials.gov registration, RBQM risk dashboards

Why it is hard

21 CFR Part 11 compliance is not a feature you bolt on. Every action writes to an append-only audit log chained with SHA-256 checksums, backed by electronic signatures and role-based access control — so the record is tamper-evident end to end.

Sentinel

From drone survey to closed work order

Drone operations · infrastructure inspection

The context

AI-powered infrastructure inspection platform. Drones fly the asset, computer vision finds the defects, and the platform turns them into tracked, assigned, SLA-bound work.

The problem

Infrastructure inspection is manual, slow and hazardous. The findings end up in photo folders and spreadsheets, disconnected from the crews who have to fix anything — so nothing is provably closed out.

What we built

  • The core loop: survey → visual and thermal imagery → YOLO26 detection → draft annotations → inspector review → work orders → field remediation → PDF report
  • Geospatial context — KML/Shapefile/GeoJSON import, LIDAR point clouds, corridor encroachment and terrain-risk analytics
  • Photogrammetry via NodeODM: orthophotos, digital surface models and textured 3D models, served as map tiles and an in-browser point-cloud viewer
  • Drone operations — flight planning with safety validation, no-fly checks against FAA/AirMap, autonomous and swarm missions
  • A PX4 SITL simulator so missions are tested in software before any aircraft leaves the ground
  • Web, native mobile and a public marketing site, all from one Nx monorepo

Why it is hard

The AI improves itself. Every annotation an inspector approves becomes labelled training data; the model is fine-tuned and redeployed. Human review is not a cost centre in this system — it is the training pipeline.

Cortex

AI track inspection from a cart and a Raspberry Pi

Railway safety · edge AI

The context

Railway track inspection system. A cart-mounted Raspberry Pi captures imagery during inspection runs, uploads it over 4G, and cloud AI identifies track defects in near real time.

The problem

Track is still inspected largely on foot. Coverage is slow, defects are found late, and there is no consistent geolocated record of what was seen on which run — which makes trends across a corridor invisible.

What we built

  • An edge capture daemon on a Raspberry Pi 5 with an Arducam IMX296 camera, GPS and a 4G HAT — geotagged imagery captured on the move
  • Local buffering and resumable upload over LTE, so a run in a dead zone is never a lost run
  • Cloud detection pipeline — FastAPI and Celery workers running YOLO models for rail cracks, missing fasteners and gauge deviations
  • PostGIS-backed findings, so every defect carries its position on the track segment
  • A Next.js operator dashboard with a Leaflet map, run history and per-finding review
  • Bot registration and API-key provisioning, so a new cart is added to the fleet in minutes

Why it is hard

Field connectivity is unreliable by default. The uploader's offline-resilience behaviour is covered by a test suite that runs on any laptop — no Pi, no camera, no track — so the hardest failure mode is verified continuously, not on site.

RDACTD

Complaints that can be trusted, tracked and measured

Enterprise integrity · multi-tenant SaaS

The context

Complaint management and business analytics platform — encrypted reporting, structured resolution, and integrity analytics for multi-branch organisations.

The problem

Serious complaints still travel by email. Reporters have no privacy and no visibility, organisations have no structured record, and neither side can show afterwards that anything was actually resolved.

What we built

  • Encrypted, evidence-backed submission flows with categorical routing and real-time status tracking
  • End-to-end resolution channels that let a reporter and an organisation lead work a case to closure
  • Organizational health dashboards for multi-branch entities, with predictive risk modelling and integrity benchmarking
  • AI-assisted pattern identification across cases, plus automated structural-health forecasting
  • Public verified profiles showing integrity scores, historical performance and resolution velocity
  • Multi-tier SaaS framework with billing, team governance and role-based administration

Why it is hard

Web and native mobile share one TypeScript core — models, service layer, tRPC client, WebSocket client, Drizzle schema and design tokens all live in shared packages. The two clients cannot drift apart, because there is only one implementation of the rules.

Open Air Construction

A contractor site built to convert, not just to exist

Commercial web · lead generation · local SEO

The context

Charlotte deck and outdoor-living contractor website — a production marketing site with a full lead pipeline behind it.

The problem

A local contractor needs more than a brochure: fast pages, trust signals, service-area coverage, and a dependable way to turn consultation requests into leads someone actually follows up — without losing editorial control or SEO.

What we built

  • Next.js 16 App Router with Tailwind CSS v4 over a custom Material 3 token layer, light and dark themes
  • A typed content layer — services, team, FAQs and metadata in TypeScript, so structural mistakes fail the build
  • An MDX blog the owner can add to by dropping in a file, rendered through a custom loader
  • Lead pipeline: contact form Server Action with Zod validation, Postgres persistence and Resend email notification
  • A protected admin inbox with bcrypt auth, lead filtering, status management and CRM sync hooks
  • Technical SEO — LocalBusiness, Service and FAQ JSON-LD, sitemap, robots, dynamic OG images

The result

A Lighthouse SEO score of 100, an editor workflow that needs no developer, and JobTread CRM plus AI enrichment already wired in behind environment keys — they switch on without touching the plumbing.
